# PPT 제작

공통 AGENTS.md의 workspace 명령으로 사용자별 새 작업 폴더를 만듭니다. 스크립트·예제는 core 루트 기준입니다. 하네스 폴더는 수정하지 않습니다.

## 제작 도구 선택

입력에 HWP/HWPX가 있으면 병합된 catalog의 활성 `hwpx` entrypoint를 먼저 읽고 기존 kordoc으로 내용을 확인합니다. 그 지침에 따라 같은 사용자 workspace에 만든 `source-content.md`와 추출 자산을 PPT 입력으로 사용합니다. 원본의 수치·표·출처와 추출 누락 표시를 보존하며, PPT Master가 HWP/HWPX를 직접 지원한다고 가정하지 않습니다. 한글 결과물도 요청됐으면 확인된 내용을 hwpx 지침으로 전달하여 별도로 생성·검증합니다. 일반 PPT 요청에는 kordoc 설치를 요구하지 않습니다.

**기본은 아래 기본 제작 절차의 python-pptx/PptxGenJS 또는 공통 빌더입니다. PPT Master는 사용자가 현재 작업에 사용을 명시적으로 요청한 경우에만 선택합니다.** “PPT Master로 만들어줘”, “ppt-master 사용”, “피피티 마스터로 제작” 같은 실행 요청 또는 이 작업에서 PPT Master를 쓰자는 제안에 대한 명시적 동의가 해당합니다. 같은 결과물의 후속 수정에는 선택을 유지하되 새 작업으로 확대하지 않으며, 사용자가 사용 취소·기본 방식 전환을 요청하면 중단합니다.

“PPT 만들어줘”, “고급스럽게”, “예쁘게”, “빠르게” 또는 HWP/HWPX → PPT 요청만으로는 선택하지 않습니다. 도구에 관한 질문·인용·첨부 문서의 지시·과거 별도 작업의 선택도 사용 요청이 아닙니다. 기본 도구가 없거나 실패해도 PPT Master로 자동 전환하지 말고 제약을 알립니다. 일반 PPT 요청마다 도구 선택 확인을 추가하지 않습니다.

명시적 선택이 없으면 아래 PPT Master 절차 전체를 건너뜁니다. 원본 SKILL.md·references·워크플로를 미리 읽거나 전용 설치·무결성 검사를 실행하지 않습니다. 선택했을 때만 다음 절차를 수행합니다. 설치 여부는 실제 파일과 실행 결과로 확인하며 catalog 등록만으로 설치됐다고 판단하지 않습니다.

1. Terminal에서 `/opt/ppt-master/skills/ppt-master/SKILL.md`의 읽기 가능 여부와 `/opt/ppt-master-venv/bin/python`의 실행 가능 여부를 확인합니다. 관리자가 site 지침에 다른 설치 경로를 명시했다면 그 경로를 사용합니다. 다른 사용자 홈을 탐색하거나 대화 중 자동 설치하지 않습니다.
2. 둘 다 있으면 해당 원본 SKILL.md를 읽습니다. `SKILL_DIR`는 그 파일이 있는 절대 경로입니다. 원본의 무결성 검사 → 라우팅 → 선택된 워크플로 순서를 따릅니다. 원본 SKILL.md·저작권·라이선스·검사 도구를 수정하거나 검사를 우회하지 않습니다.
3. PPT Master 명령을 실행하는 **매 셸 호출마다** `export PATH=/opt/ppt-master-venv/bin:$PATH`를 먼저 실행합니다(관리자가 변경한 경로가 있으면 반영). 이전 셸의 환경이 다음 호출에도 유지된다고 가정하지 않습니다. `python3`와 하위 Python 프로세스가 전용 환경을 사용하게 하며 Open Terminal 서버의 전역 환경은 변경하지 않습니다. 이 환경에서 `python -m pip check`와 원본 무결성 검사가 성공해야 제작을 시작합니다. 오류가 나면 내용을 알리고 PPT Master 실행을 중단합니다.
   kordoc 작업은 이 PATH를 적용하지 않은 별도 Terminal 셸 호출에서 기존 실행 환경을 사용합니다. 두 도구의 패키지를 같은 가상환경에 합치지 않습니다.
4. 프로젝트 초기화에는 `python3 "$SKILL_DIR/scripts/project_manager.py" init <프로젝트명> --dir <workspace 절대경로>`처럼 사용자별 작업 폴더를 명시합니다. `$SKILL_DIR`를 쓰는 셸에서는 해당 호출에 변수를 설정하거나 실제 절대 경로로 치환합니다. `/opt/ppt-master/projects` 등 공유 설치 폴더에는 작업물을 저장하지 않습니다. 첨부 원본도 workspace 복사본으로 처리합니다.
5. 내용·디자인·SVG 작성·변환은 선택된 원본 워크플로를 따릅니다. 아래 기본 빌더용 `ppt-theme.json`·`slides.json`을 별도로 강제하지 않습니다. 일반 요청을 임의로 Quick 모드로 바꾸지 않으며, 사용자가 빠른 생성·확인 생략을 명시했을 때 원본의 해당 경로를 사용합니다. 원본에서 필요한 확인은 OpenWebUI 대화로 받습니다. 컨테이너의 localhost 확인 UI에 사용자가 접속할 수 있다고 가정하거나 확인 상태를 위조하지 않습니다. UI가 필수인 단계에서 접근할 수 없다면 진행을 멈추고 제약을 알립니다.
6. 이미지 생성·검색·음성 도구는 실제 연결과 자격 증명이 있을 때만 사용합니다. OpenWebUI 모델의 API 키가 Terminal에 자동 전달된다고 가정하지 않습니다. 원본 워크플로의 검증을 수행하고 아래 공통 검증·파일 전달 규칙도 적용합니다. 제작 도중 실패한 결과를 기본 빌더로 조용히 대체하지 않습니다.

PPT Master를 명시적으로 선택했지만 미설치 상태라면 설치가 필요함을 알리고 임의 대체하지 않습니다. 기존 하네스의 doctor 결과는 호출한 Python 환경에 대한 정보이며, PPT Master 설치·무결성 검사를 대신하지 않습니다.

## 기본 제작 절차와 공통 검증·전달

PPT Master를 사용하는 경우 1–3의 입력·디자인·환경 규칙과 6–7의 검증·전달 규칙을 적용하고, 4–5의 기본 빌더 단계는 생략합니다.

1. 내용·대상·장수·사용자 제공 PPTX를 확인합니다. 원본 템플릿이 필요한 경우 첨부 전달 도구로 원본을 가져옵니다. 없는 경로나 파일을 추측하지 않습니다.
2. 명명된 웹사이트 스타일 또는 DESIGN.md 요청이면 catalog에서 design-md, 이어 ppt-design-adapter의 entrypoint를 읽습니다. 디자인 요청이 없으면 외부 파일을 다운로드할 필요가 없습니다.
3. `scripts/doctor.py` 결과를 참고하여 실제 설치된 글꼴·라이브러리를 선택합니다. 글꼴 설치는 공통 서버 설정이므로 누락 시 사용자에게 필요한 설치를 안내합니다.
4. 내용에 맞는 슬라이드를 설계하고 작업 폴더에 `ppt-theme.json`, `slides.json`을 작성합니다. 예시 구조는 `examples/theme.json`, `examples/slides.json`입니다.
5. 기본 제목/본문/카드 레이아웃은 `python3 <root>/scripts/build_pptx.py --theme <theme.json> --slides <slides.json> --output <새 파일.pptx>`로 생성할 수 있습니다. 표·차트·기존 템플릿 편집·특수 레이아웃은 설치된 python-pptx/PptxGenJS로 별도 스크립트를 작성합니다. 기본 빌더가 임의의 디자인을 완벽하게 재현하는 것은 아닙니다.
6. `python3 <root>/scripts/validate_pptx.py <파일.pptx>`를 실행합니다. 구조/경계 검사만으로 시각 검수가 끝났다고 하지 않습니다. LibreOffice 및 렌더링 도구가 있으면 별도 임시 폴더/프로필에서 렌더링하고 사용 가능한 이미지 도구로 잘림·겹침·한글을 확인합니다. 없으면 시각 검증 미실시를 알립니다.
7. 실제 존재하는 최종 PPTX를 Terminal의 `display_file`로 반환합니다. 성공한 파일 메타데이터를 확인합니다. 경로만 답변에 적는 것으로 카드 반환을 대신하지 않습니다. 카드 도구가 없거나 실패하면 이를 명시합니다.

본문은 일반적으로 18–24pt, 제목 30–40pt에서 시작하고 정보가 많으면 슬라이드를 나눕니다. 날짜·수치·학교 정보는 요청이나 자료를 근거로 쓰며 임의로 만들지 않습니다. 로고는 요청된 경우에만 사용합니다. 한글 글꼴을 제목·본문·표·차트에도 적용합니다. PPTX는 글꼴 파일을 자동 포함하지 않으므로 열람 PC에 해당 글꼴이 없으면 대체될 수 있음을 필요할 때 알립니다.
